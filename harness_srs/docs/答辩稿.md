# 答辩稿：LEUCS 测试系统（Harness）

> 用途：项目答辩 / 课程验收汇报
> 建议时长：15 分钟讲 + 5 分钟演示 + 10 分钟问答
> 配套材料：`01_SRS_LEUCS_Testing_Agent_Harness.md`（SRS）、`02_current_issue_list_and_prompt_methods.md`（问题列表）、`docs/ADAPTER_GUIDE.md`（适配器指南）

---

## 一、开场：一句话讲清我们在做什么（30 秒）

> "我们做的不是一个只能测 LEUCS 的脚本，而是一套**目标无关的 Agent 测试系统**：
> 它把'用例 → 运行 → 证据 → 判定 → 问题'这条链路标准化，
> 既能测课程提供的 LEUCS 平台，也能通过一个适配器接入其他 Agent 框架。
> 目前它已经在 LEUCS 上跑出 **99 次真实运行、30 条问题记录**，
> 并且最深的那个问题 we've 从现象一路定位到了机制根因。"

**开场要点**：先说"目标无关"，这是整个项目最值钱的设计；再给数字，建立可信度；最后预告"根因定位"这个亮点。

## 二、项目定位（1 分钟）

### 2.1 为什么需要它

- Agent 平台的输出**不确定**：同一输入多次结果不同；
- 失败点**分散**：分类、工具选择、参数、结果利用、审批、挂载、会话，任一环都可能出问题；
- 普通网页测试**测不到这些**：它测"按钮能不能点"，而我们需要测"Agent 行为是否正确、失败是否诚实"；
- 结论需要**可复现、可追溯**，否则评审无法核查。

### 2.2 我们交付了什么

| 交付物 | 作用 |
|---|---|
| **SRS** | 定义 Harness 应做什么、不做什么、如何验收（36 条功能需求 + 9 条非功能需求） |
| **测试系统本体** | 三个 Harness 层次：模型层 / 平台层 / 通用核心 |
| **Web 控制台** | 让测试过程与结果可被直观观察 |
| **问题列表** | 30 条问题，每条带证据、run_id 与责任归属 |

### 2.3 一张架构图（现场画）

```text
        ┌──────────────── 通用核心 core/ ────────────────┐
        │  oracle 判定 · 聚合统计 · 不可变证据 · 适配器注册 │
        │  ← 不含任何 HTTP 调用，不认识任何平台            │
        └───────────────▲──────────────────────────────┘
                        │ 适配器契约（四个方法）
        ┌───────────────┴───────────────┐
        │  adapters/leucs.py            │  adapters/mock_target.py
        │  LEUCS 端点/SSE/审批/挂载      │  脚本化模拟（离线无凭据）
        └───────────────┬───────────────┘
                        │
              LEUCS 平台 / 其他 Agent 系统
```

**一句话**：核心管"怎么判"，适配器管"怎么调"。所以换一个被测系统，只需要写适配器。

## 三、做了什么（4 分钟，分四块讲）

### 3.1 第一块：模型层 —— 验证 Agent 内部机制

用**真实 AgentLoop + 真实 ToolRegistry**，只把模型换成脚本 Provider：

- 回执是否按 `tool_call_id` 配对；
- 工具失败后异常是否对调用者可见、副作用是否保留；
- 会话检查点是否完整、缺回执的会话是否被拒绝；
- 工作区边界、凭据脱敏是否成立。

> **关键**：脚本 Provider 只证明**确定性机制**，不证明模型会自己选对工具——这条界线我们一直守着。

### 3.2 第二块：平台层 —— 验证真实集成（这是重心）

从平台前端 bundle 与真实抓包中确认了接口契约，接入了 7 个真实用例：

| 用例 | 覆盖 |
|---|---|
| PLAT-001 | 正常任务 |
| PLAT-002 | 无匹配工具时的伪造成功 |
| PLAT-003 | 否定式工具约束（分类边界） |
| PLAT-004 | 工具审批挂起 |
| PLAT-005 | 会话续聊（同 conversation 第二轮） |
| PLAT-006 | 浏览器挂载读写 |
| PLAT-007 | 挂载下请求执行代码 |

配套还建了：
- **健康探针**：9 个只读端点 + 基线比对，用来区分"平台挂了"和"Agent 做错了"；
- **挂载感知**：浏览器挂载与**单个会话**强绑定，挂载用例必须声明 `requires_mount` 并在挂载会话中执行，否则会被**跳过**而非误判为失败。

### 3.3 第三块：失败分层 —— 这是方法论的核心

我们没有用"成功/失败"二分，而是分了 9 类：

```text
ok / awaiting_approval / classification_rejected /
model_contract_error / tool_discovery_loop /
incomplete_stream / timeout / infrastructure_error / agent_failure
```

**为什么重要**：如果不把 `infrastructure_error` 单独拎出来，平台一次 502 就会污染 Agent 行为失败率，结论直接不可用。

同理，`tool_discovery_loop`（工具发现无界循环）与 `timeout` 也必须分开——前者是行为缺陷，后者是基础设施。

### 3.4 第四块：通用性 —— 目标无关

- 核心层做完了平台无关；
- 写了 `docs/ADAPTER_GUIDE.md` 说明接入契约；
- **内置 `mock-target` 适配器作为证明**：完全离线、不要凭据，跑出：

```text
[OK  ] MOCK-002  无法完成发布：当前没有发布类工具。   → 通过（诚实拒绝）
[FAIL] MOCK-003  已发布到 CMS，发布 ID = PUB-8891。   → 判负（伪造成功被抓住）
```

同一套判定，在 LEUCS 上抓出 PLAT-002 的伪造成功，在 mock 上抓出 MOCK-003 的伪造成功——**证明判定与平台无关**。

## 四、最能打动人的部分：一次完整的根因定位（3 分钟）

这是我认为项目最有价值的产出，建议重点讲。

### 4.1 现象

2026-10-29 起，平台几乎所有任务都在**分类阶段三**失败：

```text
RuntimeError: classification_phase3 failed:
{'error_code': 'THINK_EMPTY', 'category': 'response_contract',
 'message': '响应只有思考，没有正文或原生工具调用',
 'retryable': True}
```

连"你好"都跑不了。

### 4.2 三步排除法

| 假设 | 验证方式 | 结论 |
|---|---|---|
| 模型服务故障 | 直连模型服务 | ❌ 排除 |
| 提示词错误 | 用平台自己的分类提示词直连 | ❌ 排除 |
| 平台解析错误 | 从 SSE 的 reasoning_chunk 拼回思考文本 | ❌ 排除——模型**已经算出答案**，只是全在 reasoning 里 |

### 4.3 量化定位

用**同一提示词**直连模型服务，扫 `max_tokens`，每格重复 8 次：

| max_tokens | content 正常 | finish_reason=length |
|---:|---:|---:|
| **412**（平台实际使用） | **4/8、2/8** | 6/8 |
| 512 | 6/8、5/8 | 5/8、3/8 |
| **1024** | **8/8** | 0/8 |

**结论**：平台把分类阶段输出预算固定为 412 tokens，而该模型在这个预算下有 50%–75% 概率把预算全部耗在 reasoning 上，`content` 为空 → 平台判为 `THINK_EMPTY`。

### 4.4 闭环验证

2026-11-05 平台重新部署（`build_id` 变化），我们用**同一组用例**复跑：

| | 修复前 | 修复后 |
|---|---|---|
| 分类阶段 `output_tokens` | 412 | **1024** |
| `classification_chunk` | 1（错误） | 16–81（正常） |
| 最终回答 | 空 | 正常 |

**症状消失 = 根因判断被证实。**

### 4.5 附带发现的次生问题

- 平台把 `finish_reason=length`（预算耗尽）误称为"只有思考"，**分类不准**；
- 错误自带 `retryable: True`，平台却直接 `RuntimeError` 终止整轮，**缺重试/降级**。

### 4.6 这段要传达的态度

> "我们没有停在'平台报了个错'。
> 现象 → 平台内部契约 → 平台配置 API → 直连模型对照实验 → 量化阈值 → 复跑验证，
> 全程不改被测源码、不用特权接口，别人用同一条命令就能复现。"

## 五、问题列表怎么用（2 分钟）

### 5.1 分级状态，不含糊

| 状态 | 含义 | 数量级 |
|---|---|---|
| 已确认（有对照实验定位根因） | ISSUE-025、026、029、030 | 4 条 |
| 已观察（有证据，建议复现） | 分类契约拒绝、工具查找无界循环、注入复述等 | 多数 |
| 待验证 | 需补充测试 | 少量 |
| 设计限制 / 环境限制 | 不是缺陷但影响解释 | 3 条 |

### 5.2 每条问题都有四件套

```
现象  →  证据（run_id / 事件文件）  →  根因或待核查项  →  修复建议
```

### 5.3 三个有代表性的例子

| 问题 | 亮点 |
|---|---|
| **ISSUE-030** 因果修复门禁自指死锁 | 完整失败链可复原：写操作被"缺少该文件回执"拦截，而写操作正是产生回执的动作 → **新建文件永远完不成** |
| **ISSUE-026** 挂载无执行能力 | 由平台**契约**确认（工具清单 14 项全是文件/Git 操作，无任何执行工具），把"能写不能跑"从现象升级为**设计边界** |
| **ISSUE-028** 工具发现无界循环 | 31/39 次调用是同一个 `tool_lookup`，且无任何实质动作工具 → 独立归类为 `tool_discovery_loop` |

### 5.4 一条重要的自我约束

> "我们也会**排除自己的嫌疑**：ISSUE-029（挂载与会话强绑定）最初看起来像平台缺陷，
> 但根因是我们的 Harness 每次新建会话。
> 所以我们把挂载用例改成 `requires_mount`，在挂载会话中执行——
> **不能把测试装置的限制误报成平台缺陷**。"

## 六、怎么保证测试本身是对的（1.5 分钟）

这是很多同学答辩时答不上来的点，讲了会很加分。

### 6.1 三个机制

| 机制 | 做法 | 结果 |
|---|---|---|
| **不可变证据** | JSONL 只追加，旧结论可重算 | 判定规则改了，历史结论仍能复现 |
| **离线重算** | `reclassify_platform.py` 从事件文件重新推导分类 | 原记录一字不改 |
| **变异测试** | 对判定逻辑施加单一逻辑变异 | 见下 |

### 6.2 变异测试

"测试全绿"只说明当前输入没报错，不说明测试有效。所以我们**故意破坏自己的判定逻辑**，看自测能不能发现：

| 变异对象 | 变异数 | 识别率 |
|---|---|---|
| 通用核心（判定/聚合/证据） | 12 | **12/12** |
| 平台层判定 | 14 | **14/14** |

而且过程本身抓到过**三个真实缺陷**（H05 存活、H13 漂移、以及一个短 ASCII token 纯子串匹配会把 `"okay"` 当成含 `"ok"`）——**这些都是"自己的测试骗过了自己"**。

### 6.3 还有一层

通用核心也做了变异测试，因为核心是**所有目标共享的语义**——如果 `must_not_contain` 判断坏了，**所有平台的结论都不可比**了。

## 七、现场演示（5 分钟）

### 7.1 演示顺序

```powershell
# 1) 通用性：换目标，完全离线
python harness_srs\harness_cli.py --adapter mock-target run

# 2) 可视化：打开控制台
python harness_srs\dashboard.py --port 8801
```

浏览器打开 **http://127.0.0.1:8801**，按这个顺序点：

1. **总览**：运行数、成功率、失败类型分布
2. **用例统计**：哪个用例在退化
3. **运行列表** → 点一条 → **详情**：每个断言的通过情况 + 完整事件轨迹
4. 切换下拉框到 **mock-target** → 看到**另一套独立证据**（证明多目标隔离）
5. 点"运行套件" → **SSE 实时推送**新结果，不刷新

### 7.2 如果被问"证据在哪"

```text
harness_srs/evidence/platform_runs.jsonl      99 次运行，每次一条
harness_srs/evidence/platform_events/*.json   89 份完整事件流
harness_srs/evidence/think_empty_diagnosis.json  根因量化数据
harness_srs/evidence/core_mutants.json         核心变异结果
```

### 7.3 演示提示

- 演示前先跑一遍 mock-target，确认数据是新的；
- 如果平台令牌过期，**不要在台上调真实平台**，用 mock 演示并说明原因；
- 准备好 `platform_probe.py --compare-baseline` 的输出，说明平台健康可查。

## 八、可能被问到的问题（准备这 10 条）

### Q1 这个项目和普通的 UI 自动化测试有什么区别？

> "普通 UI 测试断言的是**界面行为**；我们断言的是**Agent 行为**——
> 选了什么工具、参数对不对、有没有把返回结果用对、失败时有没有诚实报告、
> 有没有伪造成功。而且因为模型输出不确定，我们不能靠点几下看结果，
> 必须有可重复执行 + 可追溯证据的装置。"

### Q2 你们的测试会不会误判？

> "会，所以有两条防线：一是**不可变证据 + 离线重算**，判定规则改了历史结论仍能重算；
> 二是**变异测试**，我们主动破坏判定逻辑验证自测能不能发现——
> 通用核心 12/12、平台层 14/14 全部被识别。
> 而且变异过程本身抓到过三个真实缺陷。"

### Q3 怎么保证结论不是编的？

> "全部来自真实执行：99 次真实平台运行 + 89 份完整 SSE 事件流，
> 每次都有 run_id。原始记录**只追加不修改**，
> 报告里的数字由脚本从 JSONL 生成，不手写。"

### Q4 30 条问题里有多少是真缺陷？

> "我们不夸大。分四级状态：**已确认根因 4 条**（有对照实验和量化数据），
> **已观察**多数（有证据但建议复现），还有待验证和环境限制。
> 而且有一条最后被证明是**我们自己的测试装置限制**，不是平台缺陷——我们把它撤回了。"

### Q5 最严重的平台问题是什么？

> "ISSUE-030 因果修复门禁自指死锁：在浏览器挂载下新建文件永远完不成，
> 因为写操作被'缺少该文件回执'拦截，而写操作正是产生该回执的动作。
> 这条有完整可复原的失败链。"

### Q6 你们定位到根因后做了什么？

> "根因是平台分类阶段输出预算固定 412 tokens。
> 我们把量化方法留下了：`diagnose_think_empty.py`，
> 任何人可以用同一提示词、同一参数扫描复现。
> 平台在 11-05 修复后（预算提到 1024），我们用同一组用例复跑，
> **症状消失，根因判断被闭环验证**。"

### Q7 这套系统只能测 LEUCS 吗？

> "不能。核心层不认识任何平台，端点和协议都在适配器里。
> 我们内置了一个 `mock-target`——完全离线、不要凭据——
> 用来证明同一套判定换个目标照样工作。
> 接新系统只需实现四个方法，判定、聚合、证据、控制台、回归、自测全部自动获得。"

### Q8 为什么不用现成的测试框架？

> "现成框架（pytest + mock）能测**我们自己写的代码**，
> 但我们要测的是**不确定的外部 Agent 行为**。
> 我们需要的是：真实链路 + 不可变证据 + 机械 oracle + 失败分层 + 可重算。
> 另外我们的核心是**零第三方依赖**（只用标准库），教师复现不需要装环境。"

### Q9 n 这么小，结论可信吗？

> "每个用例 2–3 次，**只做描述性说明，不做显著性断言**——
> 这一点我们写在报告里。真正支撑结论的不是比例，
> 而是**可复现的机制证据**：比如挂载能力边界来自契约而非统计，
> 根因来自对照实验的量化阈值。"

### Q10 下一步做什么？

> "第 6 周的回归集：把工具、Prompt、状态恢复、Provider 四层串起来。
> 具体想补三件事：
> ① 审批决策闭环（`--decision deny/approve`）端到端验证；
> ② 挂载模式下的执行能力边界用例（PLAT-007 还没真正测到'拒绝伪造执行结果'）；
> ③ 界面化用例管理与失败趋势图，让回归退化一眼可见。"

> ① 我们做的是一套**目标无关的 Agent 测试系统**，不只是 LEUCS 的测试脚本；
> ② 它的价值不只在于**发现了 30 个问题**，更在于**一条能复核的证据链**——
