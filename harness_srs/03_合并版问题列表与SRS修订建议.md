## 一、先说结论

### 1. 当前最值得纳入问题列表的新增问题
今天你自测到的新问题，最值得保留的是下面几类：

1. **否定式工具约束触发分类阶段运行时错误**
2. **调用不存在工具触发分类阶段校验错误**
3. **未挂载项目时执行类任务触发分类校验错误**
4. **确认 / 询问类提问触发分类阶段校验错误**
5. **浏览器挂载模式下最终验收失败**
6. **浏览器挂载模式下完整代码执行任务终答反复被拒**
7. **连续分类失败导致会话状态污染**

这些问题的共同点是：
- 不只是“回答不准”；
- 更多是**平台前置分类 / 能力所有权 / 挂载能力校验**在任务尚未进入执行前就失败；
- 说明 Harness 不能只测执行链路，也要覆盖**分类阶段、能力准入、挂载模式、会话恢复**。

### 2. 这对你现在 Harness 设计意味着什么
你原来的测试重点主要是：
- 工具调用；
- 参数边界；
- 失败恢复；
- 结果利用；
- 预算控制。

现在应补充：
- **分类阶段容错**；
- **能力边界与权限校验**；
- **挂载模式差异**；
- **会话状态污染与可恢复性**；
- **前置校验错误 vs 业务错误的区分**。

## 二、合并版问题列表（当前可直接放入问题清单）

### ISSUE-001：否定式工具约束触发分类阶段运行时错误
- **状态**：已观察，待重复验证
- **来源**：今天手工测试
- **具体 Prompt**：`运行 fibonacci.py，不要调用演示文稿工具。`
- **描述**：当用户只是用否定式表达约束，而不明确指定目标工具时，系统在分类第三阶段校验失败，抛出底层运行时错误，任务终止在分类阶段。
- **预期行为**：系统应识别否定式约束，不把“不要调用 X”误判为必须调用 X；即使无法分类，也应给出可理解的错误提示。
- **实际行为**：分类阶段直接失败，无法进入执行。
- **影响**：高
- **风险类型**：分类器容错不足 / 提示解释错误 / 用户输入约束处理失败

### ISSUE-002：调用不存在工具触发分类阶段校验错误
- **状态**：已观察，待重复验证
- **来源**：今天手工测试
- **具体 Prompt**：`调用天气查询工具，查询北京今天的天气。`
- **描述**：用户要求调用系统中未注册、不存在的工具时，系统在分类阶段直接触发能力所有权校验失败，没有友好提示，也没有进入工具查找或调用环节。
- **预期行为**：系统应明确说明工具不存在或当前能力不可用。
- **实际行为**：直接抛运行时错误，分类失败。
- **影响**：高
- **风险类型**：能力缺失提示缺失 / 错误信息不友好 / 前置校验过严

### ISSUE-003：未挂载项目时执行类任务触发分类校验错误
- **状态**：已观察，待重复验证
- **来源**：今天手工测试
- **具体 Prompt**：`编写并运行 Python 代码计算 1 到 100 的和。`
- **描述**：未挂载任何项目目录时，提交包含代码运行和结果验证义务的任务，系统判定证据所有者为空，校验失败，直接报错，没有挂载引导提示。
- **预期行为**：系统应提示用户先挂载项目，或解释当前无法执行的原因。
- **实际行为**：直接分类错误，无法给出可操作提示。
- **影响**：中高
- **风险类型**：前置环境约束提示不足

### ISSUE-004：确认 / 询问类提问触发分类阶段校验错误
- **状态**：已观察，待重复验证
- **来源**：今天手工测试
- **具体 Prompt**：`你现在能操作挂载区吗，能的话列出挂载目录文件`
- **描述**：确认系统是否具备某能力的提问，经过分类修复模块多次迭代后仍无法生成合法任务关系结构，最终校验失败，任务直接终止。
- **预期行为**：系统应支持能力确认类问题，并能回答是否可操作，再决定是否列出目录。
- **实际行为**：直接分类失败。
- **影响**：中高
- **风险类型**：询问/确认类任务建模不足

### ISSUE-005：浏览器挂载模式下文件观察任务最终验收失败
- **状态**：已观察，待独立复现
- **来源**：今天手工测试
- **具体 Prompt**：`检查我挂载目录里的 Python 代码写了什么`
- **描述**：浏览器本地挂载项目时，文件读取和目录扫描可以执行，但最终总结验收阶段触发挂载能力错误，无法输出最终答案。
- **预期行为**：文件观察任务应完整返回最终摘要。
- **实际行为**：执行阶段通过，但验收阶段失败。
- **影响**：中高
- **风险类型**：挂载能力边界不一致 / 验收链路错误

### ISSUE-006：浏览器挂载模式下完整代码执行任务终答反复被拒
- **状态**：已观察，待独立复现
- **来源**：今天手工测试
- **具体 Prompt**：`编写一个 Python 函数计算斐波那契数列第 20 项，写入 fibonacci.py 文件，运行代码验证结果，如果结果错误就自行修改，直到输出正确结果。`
- **描述**：在浏览器本地挂载项目时，编写-运行-验证-修改闭环任务反复重试后被暂停，浏览器挂载缺少项目验收权限，Agent 无法闭环。
- **预期行为**：系统应要么支持完整闭环，要么明确提示当前挂载模式不支持验收或运行。
- **实际行为**：反复重试，最终暂停。
- **影响**：高
- **风险类型**：挂载模式能力不完整 / 任务闭环缺失

### ISSUE-007：连续分类失败导致会话状态污染
- **状态**：已观察，待重复验证
- **来源**：今天手工测试
- **具体 Prompt**：先连续发送 2~3 条触发分类错误的指令，再发送 `你好`
- **描述**：同一会话连续多次触发分类错误后，分类器状态异常，后续发送原本可以正常处理的指令也会校验失败，整个会话失效。
- **预期行为**：系统应能从错误中恢复，至少保证后续会话可用。
- **实际行为**：后续正常指令也失败。
- **影响**：高
- **风险类型**：会话状态污染 / 可恢复性不足

## 四、测试方法 / Prompt 补充（可直接执行）

### METHOD-A：否定式约束
- Prompt：`运行 fibonacci.py，不要调用演示文稿工具。`
- 检查点：
  - 是否进入执行；
  - 是否把“不要调用”误解为必须调用；
  - 是否给出可理解错误。

### METHOD-B：不存在工具
- Prompt：`调用天气查询工具，查询北京今天的天气。`
- 检查点：
  - 是否识别工具不存在；
  - 是否给出友好提示；
  - 是否出现分类阶段崩溃。

### METHOD-C：未挂载项目时执行代码
- Prompt：`编写并运行 Python 代码计算 1 到 100 的和。`
- 检查点：
  - 是否提示先挂载项目；
  - 是否给出运行依赖说明；
  - 是否错误终止。

### METHOD-D：能力确认类问题
- Prompt：`你现在能操作挂载区吗，能的话列出挂载目录文件`
- 检查点：
  - 是否能回答能力是否可用；
  - 是否支持继续列目录；
  - 是否直接分类失败。

### METHOD-E：浏览器挂载模式观察任务
- Prompt：`检查我挂载目录里的 Python 代码写了什么`
- 检查点：
  - 文件读取是否成功；
  - 最终摘要是否输出；
  - 是否出现验收阶段错误。

### METHOD-F：浏览器挂载模式闭环代码任务
- Prompt：`编写一个 Python 函数计算斐波那契数列第 20 项，写入 fibonacci.py 文件，运行代码验证结果，如果结果错误就自行修改，直到输出正确结果。`
- 检查点：
  - 是否完成写-跑-验闭环；
  - 是否反复重试；
  - 是否提示挂载模式不支持完整闭环。

### METHOD-G：会话状态污染
- Prompt：先连续发送 2~3 条会触发分类错误的指令，再发送 `你好`
- 检查点：
  - 后续正常指令是否还能执行；
  - 是否需要新开会话恢复；
  - 错误是否会跨轮次扩散。

## 五、SRS / 测试系统需要补充的设计点

基于今天的新问题，建议 Harness 的 SRS 至少补上这些设计：

### 1. 前置分类阶段可观测性
- 记录分类阶段、校验阶段、执行阶段；
- 区分：
  - 分类失败；
  - 能力缺失；
  - 挂载能力失败；
  - 工具调用失败；
  - 最终回答失败。

### 2. 错误可理解性
- 对“不存在工具”“未挂载项目”“能力不可用”这类问题，必须给出用户可理解提示；
- 不应只抛底层运行时错误。

### 3. 挂载模式矩阵
- 需要区分：
  - 无挂载；
  - 本地文件挂载；
  - 浏览器挂载；
  - 代码执行挂载；
  - 有验收权限 / 无验收权限。

### 4. 会话恢复测试
- 连续失败后，测试会话是否可恢复；
- 支持“新会话重放”和“同会话恢复”对比。

### 5. 分类器 / 能力边界测试
- 否定式约束；
- 不存在工具；
- 能力确认问题；
- 证据所有者为空；
- 任务关系结构生成失败。

### 6. 验收阶段独立性
- 文件读取可以成功不代表最终总结一定成功；
- Harness 要单独记录“最终验收失败”作为独立失败模式。

### 7. 问题分级与归类
建议问题分为：
- 平台前置校验问题；
- Agent 行为问题；
- 工具选择问题；
- 参数问题；
- 结果利用问题；
- 会话状态问题；
- 环境 / 挂载模式问题；
- 测试框架自身问题。

## 六、对 SRS 的修订建议（可直接合并进原 SRS）

建议在 SRS 的“功能需求”里新增以下条目：

### FR-新增-01：前置分类阶段测试
系统应支持记录任务在分类、能力校验、挂载检查、执行、验收各阶段的状态。

### FR-新增-02：能力边界提示
系统应支持检测以下情况：
- 工具不存在；
- 未挂载项目；
- 挂载能力不支持当前任务；
- 能力确认类提问；
- 否定式工具约束。

### FR-新增-03：会话状态恢复
系统应支持测试连续失败后会话是否仍可用。

### FR-新增-04：验收阶段失败独立标记
系统应把“最终验收失败”和“工具调用失败”分开记录。

### FR-新增-05：挂载模式矩阵
系统应支持按挂载模式选择测试用例，并标注是否可执行、可验收、可回滚。
